================================================================================
THE TASK
================================================================================

Build `src/ui` — the design system — as **components and composites**, never as
`ComponentDefinition`s.

    A component has no logic. Props in, description out.
    A composite has state. Created per use, renders itself.

`spec/ui/vocabulary.md` sorts all fourteen for you: **ten components, one
composite (`ui.Form`), plus `ui.ActionButton` and `ui.ActionCard` which are new
and are composites.** Build them in that document's language and do not
re-litigate the sort — if one is wrong, say so in a comment and fix the spec
with the code.

**Nothing in `src/ui` may call `document.createElement`.** The old `entityList.ts`
was 211 lines of imperative DOM, a `WeakMap<Element, HTMLElement>`, manual
`header.remove()` and `[data-status]` toggles — for a sidebar with a heading, a
count and three states. That is the thing being deleted. Assert it with a test
over the source, because it is the only way it stays true.

================================================================================
THE TWO THAT ARE NEW, AND WHY THEY MATTER MOST
================================================================================

**`ui.ActionButton`** takes a **command** and nothing else. A command now carries
`available(): Availability` and, when it needs one, `confirm`. So:

  * refused → visible, disabled, labelled with `why` (states §4)
  * running → says what it is doing, cannot be fired twice (rules §3)
  * confirmable → asks first (rules §7)

None of that is the caller's to remember. **Getting it wrong should take effort.**
This one component closes what the roadmap called U2 and U3, and they were one
gap wearing two names.

**`ui.ActionCard`** is a command with inputs: title, the consequence in a
sentence, the fields, one primary control, and the result or the error in place.

**Generate the fields from the command's input schema.** `CommandContract.input`
carries JSON Schema precisely so a form does not have to be written by hand —
that is rules §6 (*never a bare `<textarea>` of JSON*) and it is why `PeopleApi`
ended up carrying twelve loose form buffers. Where the schema genuinely
under-describes an interaction, hand-write **one field**, not the whole form.

================================================================================
STATES
================================================================================

    type EntityListStatus = 'loading' | 'ready' | 'empty' | 'error';

Four. Not the old five and not three. `refused` and `unauthenticated` are **not
list states** — they are answers to *may I*, which is `Availability`, and a list
you may not read is a list whose read command is unavailable. Modelling them as
statuses is what made every app hand-roll them differently. `idle` is gone: it
was `unauthenticated` wearing a costume.
