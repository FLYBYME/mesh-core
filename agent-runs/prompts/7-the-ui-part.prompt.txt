================================================================================
WHAT TO BUILD
================================================================================

A new **Extension** part in this repository, `src/ui/`, following the file shape
every other part here now has (`contract.ts`, `views/`, `index.ts`).

**Start from the duplication that was measured, not from what a design system
usually ships.** `agent-runs/reports/6-sections-are-functions.md` §4 compared the
two decomposed consoles line by line. Read it — it is the requirements document,
and it found four repeated shapes:

- **the entity list sidebar** — a fixed-width scrolling pane, an uppercase header
  with a count, then *the same three branches in both consoles*: `loading` → muted
  text, `error` → a card at `rgba(248,81,73,0.1)` with `1px solid #f85149`,
  `ready && empty` → a muted message. Then list items as full-width buttons with a
  selected state at `1px solid var(--accent)`.
- **the detail surface** — an empty-selection placeholder card, then a `Card` at
  `padding: 16px` / `var(--chrome)` / `1px solid var(--edge)` / `borderRadius: 6px`
  with a title and a badge.
- **the property grid** — `Grid` at `140px 1fr` or `180px 1fr`, every row a bold
  `Span` label then a value, monospace for hashes.
- **the table** — **neither console had one**, so both hand-stitched a header row
  out of `Grid` plus a `Stack` with borders and rounded corners.

Build in that order. Four is enough for one dispatch. **A vocabulary is discovered
by use** — the next ones come from the second console telling you what is missing.

Read `mesh-web/spec/components.md` for `Nav` and the focus graph before deciding
whether it belongs in this round; it is the first component that would need
arrow-key movement within a group, which is specified and unbuilt.

================================================================================
THE CONSTRAINT THAT SHAPES ALL OF IT
================================================================================

**A prop cannot be a function taking arguments.** From `description/types.ts`:

```ts
export type Props = { readonly [name: string]: Reactive<Json> | undefined };
export type Reactive<T> = T | (() => T);
export type Json = string | number | boolean | null | readonly Json[] | { … };
```

So a prop may be a value or a **getter returning a value**, and nothing else.
Report 6 recommends `ui.entityList({ items, renderItem, onSelect })` — **that
cannot exist.** `renderItem` takes an item and returns a Node; it is neither Json
nor a getter of Json. Do not try to widen `Props` to allow it; the exactness of
`Props` is why a prop typo is a compile error (`spec/type-safety.md` §4).

**A component takes props and children. Per-item rendering belongs to the caller**,
who writes the `each()`. So the sidebar component owns the frame — width, border,
scroll, header, and the loading/error/empty presentation — and the caller supplies
the rows.

### Which means there is a real choice to make, and the report did not see it

Two ways to package a repeated shape:

- **a component** — a name in the registry, resolved **at render time**. Updating
  `ui` and recomposing updates every site. **Late-bound.**
- **a helper function** exported from `ui` — a plain function returning a Node,
  bundled into the *consumer's* artifact at build time. Updating it means
  rebuilding and republishing every consumer. **Early-bound**, and it couples two
  independently versioned artifacts, which is the hazard
  `~/code/surfdns/architecture/boundaries.md` names.

> **Anything that should improve for every site by recomposing must be a
> component, not a helper.**

Push as much as possible into components. If something genuinely cannot be one,
say why in the report — that list is the most useful thing this dispatch can
produce, because it is the shape of what the description layer cannot express.

**The loading/error/empty case is the test.** It looks like it needs a callback
and it does not: `status` is a prop, the rows are children, and the component's
own CSS decides what shows. Something like

```ts
element('ui.EntityList', {
    props: { status: () => sites.status(), emptyMessage: 'No sites yet' },
    children: [each(...)],
})
```

with `[data-status="loading"] > *` hidden and the message supplied by the
component. **Verify that this actually works before building four components on
it** — if it does not, the whole vocabulary needs a different shape and that is
worth finding out in the first hour.

### The rule every component follows

> **Reach for the native element whose accessibility you would otherwise rewrite.**

`Input` already maps to `<input>` and passes `type` through, so
`<input type="range">` renders today and brings arrow keys, Home/End and Page
Up/Down — the non-pointer path `input.md` §3 *requires* of every action. The
kernel already follows this rule: `Dialog` uses `<dialog>` for top layer with no
z-index arithmetic, `Heading` picks a real `h1`–`h6`. A design system that reaches
for `div` inherits the maintenance of every behaviour a browser already ships.

### Styling: CSS, not TypeScript

`ui` ships a **stylesheet** with its artifact (C8 — a part imports a `.css` file,
esbuild emits it, the cdn emits a `<link>`). Values come from the thirteen theme
tokens that already exist:

```
--page  --chrome  --surface  --surface-hover  --ink  --ink-dim
--edge  --accent  --on-accent  --info  --warn  --error  --shadow
```

**Wrap every rule in `@layer`.** This is not decoration and it removes a problem
rather than working around one: `mesh-serve/src/cdn/methods/page.ts` emits part
stylesheets **alphabetically by part id**, so `ui` loads after `calc`, `catalog`
and `chrome`. In the CSS cascade an **unlayered** declaration beats a **layered**
one regardless of source order — so `ui` in a layer is overridable by an
application's own unlayered CSS no matter what order the links appear in.

That means **no change to `page.ts` is needed**, which is the point: the ordering
is solved inside this part rather than by a rule about filenames. Verify it in a
browser test rather than trusting this paragraph.

AND ADOPT IT — same dispatch
================================================================================

**A capability with no consumer is not done** — `~/code/surfdns/decisions/0001`.
`models` shipped with zero production readers and its first adoption found, in a
day, that it does not refresh after mutations made through explicit contracts.

So this dispatch also **adopts `ui` in one console** — pick `catalog` or

the inline styling it replaces. The other console follows later.

`catalog` and `releases` must declare `requiredParts: [{ id: 'ui', version: '^0.1' }]`
in `mesh.json`. `checkComposition` already refuses a release missing a required
part, so nothing new is needed for that — confirm it and say so.

================================================================================
WHAT NOT TO DO
================================================================================

**Do not build a layout system.** `Stack`, `Row` and `Grid` are kernel primitives.
Primitives own structure; `ui` owns appearance and composite widgets. A second
layout system over `Grid` is two ways to do one thing.

**Do not add components nothing asked for.** Every component in this dispatch must
replace something a real part is writing today. If you cannot name the call sites
it deletes, it does not go in.

**Do not touch `chrome` or `auth`.** They are live on all six sites and adopting
`ui` in the shell is a later, more careful dispatch.

**Zero `as any`, zero `as never`, zero casts.** Foreground commands, commit as you
go.
