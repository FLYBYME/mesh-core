================================================================================
THE TASK
================================================================================

Composing a release is currently a **textarea** you type `part-id: ^range` into,
one line each, parsed by hand in `src/releases/parse.ts`. It works, and it is
precisely what the form vocabulary exists to replace: free text standing in for
a structured input the server already describes.

`GET /api/_describe` serves `cdn.compose`'s input schema. Build the form from
that, via `renderForm`, rather than from a parser.

**Parts are a repeating group** — id plus version range. That is the first real
test of whether the vocabulary handles an array of objects. If it does not,
**say so and report it** rather than reaching back for a textarea; a finding
about the vocabulary is worth more here than a screen that quietly avoids it.

Keep what the current console gets right:

  * **Dry run before compose**, one click away. Resolving and reporting problems
    without writing anything is the whole reason composing is safe.
  * Every problem reported at once, not the first — `cdn.compose` returns them
    as a list deliberately, because somebody composing five parts wants five
    answers rather than five round trips.
  * `cx.confirmation.ask` before deploying. A deploy changes what a hostname
    serves to the internet.

If `renderForm`'s override seam cannot express something this screen does, that
is the interesting result. The seam exists for genuine exceptions; a seam used
for everything is a seam that is not working, and I would rather hear that than
have it papered over.
