The console is going from two views to seven. Close the vocabulary gaps now,
before seven screens each work around them differently.

**Read `mesh-operator/spec/apps/console.md`** — the plan, written against a live
cluster — then `spec/ui/anatomy.md`, `spec/ui/states.md` and `spec/roadmap.md`
Track U. This dispatch is mesh-core's half of that plan: the console cannot be
built well out of what the vocabulary currently offers, and the evidence is that
`mesh-operator/src/console/views/sites.ts` already hand-writes things that belong
here.

--------------------------------------------------------------------------------
PART 0 — U7, AND IT COMES FIRST BECAUSE IT IS MEASURED

Do this part before the others. It is not a guess about what seven views will
need: two of them are written, in `mesh-operator`, and they do not compile.

A dispatch there wrote `catalog` and `fleet` against this vocabulary and stopped
with **28 typecheck errors**. Read together they are three problems, and all three
are this repository's rather than the caller's. `spec/roadmap.md` U7 has the full
account with the error counts. In short:

1. **Eleven of the fourteen names in `ui` return a `Node` and three return state
   with a `view()`, and the call site cannot tell which.** The same author got it
   wrong in both directions within one file — put `ui.ActionCard(…)` into a
   children array, and called `.view()` on `ui.PropertyGrid(…)`.

2. **The namespace is not generic.** `createActionCard<I, O>` is; `ui.ActionCard`
   is declared `Composite<ActionCardProps<Record<string, Json | undefined>,
   unknown>, …>` and `ui.ActionButton` as `ActionButtonProps<unknown, unknown>`,
   so the type parameters are pinned to their defaults **at the export**. A real
   `BoundCommand<BuilderImportRepoInput, …>` therefore does not fit, and neither
   does a typed `input`. The vocabulary that every screen is told to use cannot
   accept a typed command.

3. **Four props were invented** because the real ones are not discoverable —
   `items` on `EntityListProps`, `subtitle` on `DetailSurfaceProps`, `button` on
   `FormOverrides`, and a `{ header, value }[]` for `PropertyGrid`. Each is a
   guess at the obvious name, which tells you what the obvious name would be.

(2) is the one that matters, and it is worth being blunt about why. The two ways
out of it today are importing `createActionCard` instead — the vocabulary telling
you not to use the vocabulary — or a cast. **A design system usable only through a
cast is how `as any` enters a codebase that bans it.** The next dispatch under
time pressure will find that door long before it finds the roadmap entry.

Fix the export so the generics survive it. Then decide (1) — a naming rule, a
`.view()` on everything, or one shape for all fourteen; whichever, it must be
answerable *at the call site without checking a table*. Then look at (3) and take
the guesses seriously as evidence about the names.

The test that proves this is not a unit test. **Write a type-level check that a
real typed `BoundCommand` can be passed to `ui.ActionCard` and `ui.ActionButton`
with no cast** — the errors above are compile-time, so a runtime test cannot see
them. `npm test` runs `typecheck` first, so a file that must compile is a test.

--------------------------------------------------------------------------------
PART 1 — U4: THE SCROLL MODEL, WHICH IS BLOCKING THE ANATOMY DOCUMENT

`spec/ui/anatomy.md` says INDEX and DETAIL scroll independently and a view fills
its surface without growing it. **"Fills its surface" means two different things**
under a windowed chrome, which sizes the view, and a routing chrome, which hands
it the page.

It needs one answer that works under both before `anatomy.md` can move from
Proposed to Decided — and seven views is exactly when an unsettled scroll model
starts producing seven different inline `style="display:flex;flex:1;min-height:0"`
attributes, which is what the console writes today.

Decide it. Write it into `spec/ui/anatomy.md`. Then make the components obey it,
so a screen gets the behaviour by using the vocabulary rather than by remembering
a CSS incantation. **A rule the components cannot express is a rule that will be
broken** — this track's own sentence.

Test it under both chromes, because "works under both" is the requirement and a
test under one proves the half that was never in doubt.

--------------------------------------------------------------------------------
PART 2 — A TABLE ROW NEEDS ACTIONS, AND THE CONSOLE ALREADY WORKS AROUND IT

`ui.Table` renders rows. The console's release table puts a **Deploy** button in
every row, and does it by passing a `Node` into a cell — which works, and means
the component has no idea a row has an action, so it cannot align one, disable
one, or say why one is refused.

Seven views will each want this: deploy a release, revoke a grant, assign a node,
decide an approval, remove a member. Five hand-rolled versions is the wheel `ui`
exists to stop being reinvented.

Give `ui.Table` a declared per-row action taking a `BoundCommand` and rendering it
through the same path `ui.ActionButton` uses — so a refused row action is visible,
disabled and labelled with the reason, and a running one cannot be fired twice.

**Press it in a test**, twice, and assert the command ran once and against the
right row. Asserting a button exists is not the claim.

--------------------------------------------------------------------------------
PART 3 — AN APP WITH SEVEN VIEWS NEEDS A WAY TO GET BETWEEN THEM

The console has two views and switches with a button labelled "Members" that the
other view does not have. That does not survive seven.

`src/chrome/` is where a console's tabs come from. Look at what is there before
designing anything: if the chrome already answers this, the finding is that
nothing uses it, and wiring it up is the work. If it does not, say what is missing
and build the smallest thing that serves seven views without becoming an
application switcher — **A6.2 is explicitly not in scope** and neither is a
command palette (mesh-web A8.14). U7 is Part 0 of this dispatch, not a palette.

Whatever it is, a view must be able to say *I am not available to this caller*
and have the navigation reflect it, rather than offering a tab that lands on a
refusal. That is `states.md` §4 applied to navigation, and it is the part most
likely to be skipped.

A WARNING WORTH READING, BECAUSE IT HAPPENED IN THIS FILE'S NEIGHBOUR TODAY

`ui.css` was truncated at its own header for a day: the header spelled out a
comment annotation inline, **CSS comments do not nest**, so the file ended early
and a browser swallowed the entire token layer as a bogus rule's body. Every token
was undefined on the live page and every test still passed, because the browser
tests mount components without that stylesheet.

`test/ui.source.spec.ts` now checks for it. The lesson is the one this repository
keeps relearning: **a thing that is valid to every tool that reads it as text can
be invalid to the only thing that parses it.** If you add a stylesheet, check it
is parsed, not just that it is emitted.
