U2 — THE FIVE STATES (do this first; the others depend on it)
================================================================================

    type EntityListStatus = 'idle' | 'loading' | 'error' | 'ready' | 'empty';

No `unauthenticated`. No `refused`. `spec/ui/states.md` requires all five of
every view, and the vocabulary carries three.

The proof is already in the code — `partsList.ts`:

    idleMessage: 'Sign in to view catalog parts.'

That is `unauthenticated` wearing a costume, because the type has no name for
it. `idle` is not a state a person can be in: it has either started loading or
it is waiting for a session, and those are different.

Replace it with a type carrying all five **and the refusal reason as data**, so
a view that forgets one does not compile. The shape exists already —
`mesh-operator/src/admin/contract.ts` has `Availability`:

    { can: true, gate } | { can: false, why: 'not_exposed' | 'needs_session' | 'needs_operator' | 'not_ready' }

Reuse that vocabulary rather than inventing a second one.

Every consumer updates. `EntityList` and `Table` both take a status; both get
all five; every call site says what each looks like.

================================================================================
U3 — THE ACTION CARD, AND THE TWO CONTROLS UNDER IT
================================================================================

`spec/views/action-card.md` in mesh-operator is the specification. Build:

  * **`ui.ActionCard`** — title naming the contract, a sentence saying the
    consequence, the input rows, one primary control, and the result or the
    error in place.
  * **`ui.ActionButton`** — takes an `Availability` and a pending state.
    Disabled with the reason when refused (states §4). Says what it is doing
    and cannot be fired twice while running (rules §3).

One `ActionStatus` replaces five:

    type ActionStatus = 'idle' | 'running' | 'done' | 'refused' | 'failed';

`refused` is separate from `failed`. Today none of the five cards has it, so a
gate refusal renders as a failure — a lie about a working platform. The verb
that differs in each of the five (`resolving`, `importing`, `saving`,
`releasing`) is a **label**, not a state.

Then port the five cards onto it: `importRepoCard`, `declarationCard`,
`releasePartCard`, `releaseRepoCard`, `rangeResolverCard`. Each spec in
`mesh-operator/spec/views/` says what that card specifically needs.

`rangeResolverCard` is a READ. It confirms nothing and may run as the person
types. Do not make it a write card for symmetry.

WHAT YOU MUST FIX WHILE PORTING, because each is specified and each is a defect:

  * `releasePartCard` and `releaseRepoCard` publish with **no confirmation**
    (rules §7). `release_repo` emits N `partReleased` events and rolling
    releases follow them, so one click can move every rolling site.
  * `releaseRepoCard` does not show **which parts** it will release. The screen
    has them — `app.parts()` filtered by repository.
  * `importRepoCard` disables only on status, not on an empty url.

Anything else in those specs marked as a defect that you do NOT fix, list in
your closing comment. Do not fix silently and do not skip silently.

================================================================================
U1 — DESIGN TOKENS
================================================================================

Colour, type scale and spacing exist only as literals in `ui.css`. Nothing is
named, and `views/badges.ts` carries eight literal hex colours while every
neighbouring file uses `var(--ink)`, `var(--edge)`, `var(--accent)`. Two colour
systems in one directory.

Name them once as custom properties — surface, chrome, page, edge, ink,
ink-dim, accent, on-accent, plus a danger/warn/ok triple and a spacing and type
scale — document them in `spec/ui/`, and make them the only values a component
may use.

Two real bugs this fixes, both in `badges.ts`, both specified in
`mesh-operator/spec/views/badges.md`:

  * `built` and `extension` are **the same green**, so a green badge in a row
    means two unrelated things depending on which column it is in
  * the state badge's fallback is **red**, so a state added server-side —
    `building`, `failed`, `superseded` — renders as a failure without anybody
    deciding. `building` in the colour of `failed` is a lie the screen tells
    confidently. Default neutral; red is a choice.

Do not restyle anything beyond replacing literals with tokens and fixing those
two. A visual redesign is a different PR and the human has not asked for one.
