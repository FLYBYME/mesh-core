--- 1. A form vocabulary in `ui` -------------------------------------------

`ui@0.1.0` answers the display half — `entityList`, `entityItem`,
`detailSurface`, `propertyGrid`, `table`, `tableRow`. It has **no way to enter a
record**: no field, no label, no select, no button row, no dialog.

Write it against a **JSON Schema**, not against the screens. `GET /api/_describe`
serves `input` and `output` per exposed call and the kernel can fetch it
(`fetchApiSpec`). There are ~154 addressable CRUD contracts in mesh-serve, every
one with both schemas, and zero hand-written UI for any of them.

**Four things that are not negotiable, because they are already settled:**

  * The dispatcher listens for `input`, not `change`. A form whose button is
    clicked straight from a focused field must still see the last keystroke —
    that is the classic dropped password. An empty number field is `undefined`,
    not `0`.
  * `Props = Reactive<Json> | undefined` — **per prop**. A `style` object holding
    a getter is a Json object holding a function and will not compile; make the
    whole `style` the getter. This cost time today.
  * **The override seam ships in the first commit.** Generic by default, refined
    per contract, refining *fields* rather than replacing the form. Without it
    the first screen with real requirements hand-writes its form and then every
    screen does. Same shape as `defaultFrame`: the ordinary thing, with every
    piece overridable.
  * A component is contributed through `Declarations.components` with the
    `${id}.` prefix, the way `ui/contract.ts` already does it.
