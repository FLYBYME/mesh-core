*"How do I add a new repo?"* — there is no answer in the console. `node.provision`
exists, is gated, is allowlisted, and **nothing calls it**. Same shape as every
other gap this week: built, correct, unreachable.

Add provisioning to the Fleet console.

--- The distinction the screen must keep ------------------------------------

  * **`node.provision` makes a new switch exist** — this machine *can now run*
    `dns`, because the code is on it.
  * **`node.assign` flips switches** — this machine *is running* `dns`.

Two verbs, two acts. Blur them and "what can this node run" and "what is it
running" become one confused thing, and `node.status` stops meaning anything.
`node.status` reports `provisionedServices` beside `runningServices` for exactly
this reason — **show both**.

--- The form -----------------------------------------------------------------

`node.provision`'s input schema is in `GET /api/_describe`. Build it with
`renderForm`, not by hand. Fields: hostname, name, repository, ref, and
optionally path, dependsOn, mountKey.

Two things the UI must make **true**, not merely mention:

  * **A ref is required and a branch is refused.** The server rejects `main`,
    `master` and any `refs/heads/…`. Say so in the form, before the round trip.
    A node following a branch changes behaviour when somebody else pushes — the
    mutable-version problem in a new place.
  * **This runs `npm install` on a real machine**, which runs arbitrary install
    scripts. It is the most dangerous action in the console.
    `cx.confirmation.ask` with `destructive: true`, naming **the repository and
    the machine** — not a generic "are you sure".

An allowlist refusal must read as *this repository is not permitted*, not as a
generic failure. It is a configuration answer and the person needs to know it is
the allowlist rather than their typing.
