--------------------------------------------------------------------------------

Every action the API exposes on a collection this app owns has a control.

Those three are not optional and are not "a follow-up". A person must be able
to create a site in the operator app when you are done.

Spec §4 also lists fourteen exposed tools and where each lives. Several already
have UI; `builder.import_repo`, `builder.release_part`, `builder.release_repo`
and `node.provision` do not, and they are how anything gets into the platform
at all. Wire them.

Where an action is INTERNAL on the server, the control is visible and DISABLED
with the reason — not absent (RULES §4, spec §6 "refused"). An operator who
cannot delete a release should see a disabled delete saying so, not an app that

deleted) and #70 (artifact/build internal) are already open for those; link
them from the disabled state if that is cheap.

--------------------------------------------------------------------------------
4. ROUTER PARAMS — part of the same change
--------------------------------------------------------------------------------

`src/nav/router.ts` has no params: `grep -c params src/nav/router.ts` is 0.

    export interface Route {
        readonly owner?: string;
        readonly view: string;
        readonly params?: Readonly<Record<string, Json>>;
    }

Without params, "the sites view" is linkable and "site foo.example.com" is not.
With four views folded into one app, the selection is exactly what a person
wants to paste to a colleague.

Choose the encoding, put it in `formatRoute`/`parseRoute`, and round-trip it in
a test for every shape in spec §7 — including empty params and a param
containing `/`, because a part name can contain one.

Then use it: selecting a part, release, site, group or node puts the selection
in the route, and landing on that URL restores it.
