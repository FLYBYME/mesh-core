================================================================================
THE TASK
================================================================================

Two Applications, and they are the reason this repository exists:

    src/catalog/index.ts     browse the catalog: parts, their versions, what
                             each is, who publishes it, what it was built from
    src/releases/index.ts    compose a release from version ranges, see what it
                             resolves to, deploy it to a hostname, and roll back

Add both to `mesh.json` as `kind: "application"`, version `0.1.0`, with real
`description` and `keywords` — this repository's own parts should not be the ones
with empty descriptions in a catalog browser you are writing.

**This is the platform managing the platform.** The spec is
`mesh-serve/spec/managing.md`; read §0 and §4 before you start. A console built
any other way is a second deployment path, and a second path is one that stops
being exercised.

================================================================================
THE CONTRACTS EXIST NOW — THIS WAS BLOCKED UNTIL TODAY
================================================================================

Until 2026-09-06 the catalog had **no public contract at all**: a console could
not list parts, not because it was refused but because there was no route. That
was roadmap F2 and it is done. What you may call:

    part.find / findOne / get / count             browse parts
    partVersion.find / findOne / get / count      versions of one part
    catalog.resolve                               what a range actually resolves
                                                  to, before composing
    release.find / findOne / get / count          releases, scoped to the caller
    site.find / findOne / get / count             hostnames, scoped to the caller
    cdn.compose                                   create a release
    cdn.deploy                                    point a hostname at one

Two things follow that are easy to get wrong:

**`part` and `partVersion` are global; `release` and `site` are scoped.** A
catalog browser shows everything anybody published — that is what a catalog is.
A release list shows only the caller's own, because `scopedBy` narrows it in the
database. Do not build a filter for the second: it is already applied, and adding
one in the UI implies it was not.

**Declare what you call in `mesh.json`.** A part declares its `mesh` requirements
and a *site* decides the gate. Look at `mesh-demos/src/whoami` and its
`mesh.json` entry for the shape, and run `npm run generate` — the client is
generated by `mesh-serve client`, not hand-written, which is what stops it
drifting from the server.

================================================================================
WHAT MAKES THIS WORTH BUILDING RATHER THAN A CRUD SCREEN
================================================================================

**Compose before deploy, and show the difference.** `cdn.compose` resolves
ranges, checks the parts hold together, and returns `problems` **instead of** a
release when they do not — nothing goes live from it. `cdn.deploy` is the write
that changes what the internet sees. They are two calls on purpose and the screen
should make that obvious: resolve and inspect, then commit.

`compose` also takes `dryRun`. Use it. An operator should see what `^0.1` resolves
to *before* a release row exists.

**Rollback is the same call backwards.** A deploy is one field — `site.releaseHash`
— so a site's previous releases are deployable again with `cdn.deploy` and nothing
else. That is the single most valuable thing on the screen and it is nearly free:
list the releases, show which one is live, let any of them be made live.

**A failed build has a log and nothing reads it.** `BuildSchema` carries `log` and
`error` precisely because *a failed build with no output is a bug report nobody
can act on*, and roadmap F4 is that no reader exists. If `build.find` turns out to
be exposed, show it. If it is not, **say so in your report** — that is a finding,
not a blocker, and F2 named the exposable set deliberately.

================================================================================
THE FRAMEWORK, AND WHAT IS NEW IN IT
================================================================================

The kernel is `^0.11`, which is newer than anything in `mesh-demos` was written
against. You have primitives those apps did not:

    TextArea  ScrollView  Grid  Divider  Span    Heading now takes `level` 1..6
    Draggable / DropZone  Surface (needs('dom'))

**Use `Grid` for the version table and `ScrollView` for long lists.** The demo
apps abused `Stack` and inline `overflowY` because these did not exist; do not
copy that. `Heading({ level })` emits the right tag — a page whose every heading
is `<h2>` is wrong for a screen reader.

Read `mesh-core/src/chrome/index.ts` first. It is the only part in this
repository, it is short, and it shows the two things most likely to trip you:
**a description is data**, so an intent's action is a `command(...)` and not a
closure; and **a part cannot ship CSS**, so styling is inline `style` props for
now — with camelCase keys, which work as of kernel 0.11.2 and did not before.

================================================================================
WHAT GOOD LOOKS LIKE
================================================================================

- Both apps usable against the **live cluster**, not mocks. It is running on
  `ws://127.0.0.1:4001` with 13 real parts and 5 real sites in it.
- Browser tests per app via `mountPart`, with the mesh client stubbed — a test
  that needs a cluster is a test nobody runs.
- Every call's failure path handled and visible. A refused call is an answer, not
  an exception: `makeHttp` returns status rather than throwing, on purpose.
- `npm run typecheck` clean, **zero `as any`, zero `as never`, zero casts.**
- `npm test` green, including chrome's existing 3.
