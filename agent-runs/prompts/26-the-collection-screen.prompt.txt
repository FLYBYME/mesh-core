--------------------------------------------------------------------------------
PART 1 — THE QUERY IS ALREADY IN THE CONTRACT

**Every generated `find` already accepts all of it.** `CrudParamsSchema`
(`@flybyme/mesh/dist/interfaces/ICrudContract.d.ts:31`):

    limit         number, with a default
    offset        number, with a default
    sort          string | string[]
    search        string
    searchFields  string | string[]
    fields        string | string[]
    query         Record<string, unknown>
    populate      string | string[]

Nothing in any UI in this platform passes one of them. `cx.models(name)` fetches
and nothing else, so every list is the whole collection, unsorted, unsearchable.

So pagination, sort, limit and search are **not new server work and not new
client-side filtering.** They are parameters being passed. Wire them, and let the
server do the paging — a composite that fetches everything and slices it in the
browser is the wrong answer and will fall over on the first real collection.

Page size belongs to the caller with a sensible default. Sort by clicking a
column. Search is one input bound to `search`, debounced, and the composite must
say **which fields it is searching** rather than implying it searches everything —
`searchFields` exists because the server will not guess either.

--------------------------------------------------------------------------------
PART 2 — RICH CONTROLS, GENERATED FROM THE SCHEMA

    "no comma separated shit or raw json. they all have descriptions and
     min/max/defaults"

This is the part to take literally. A JSON Schema from a zod contract carries far
more than a field name and a type, and the current form ignores nearly all of it.
Use it:

    type: string + enum        a select, not a text box
    type: string + format      email, uri, date-time each get their own control
    type: number + min/max     a number input that enforces them, or a range
    type: boolean              a checkbox
    type: array of string      repeatable rows with an add and a remove
    type: array of object      repeatable groups, each generated from items
    type: object               a nested fieldset
    description                shown, as help text on the field
    default                    prefilled
    required                   marked, and enforced before submit
    minLength / maxLength      enforced, and surfaced as you type
    pattern                    validated

**Two things are forbidden outputs**, and both exist today:

- **A comma-separated text box standing in for an array.** `site.seed` takes
  `sources: [{ repository, ref, subdirectory }]` and the console renders one text
  box, so a per-repository ref cannot be expressed at all. An array of objects
  gets repeatable rows. That is the case that has to work.
- **A raw JSON textarea.** If a shape cannot be rendered, say so in words and name
  the field; do not hand somebody a JSON editor and call it a form.

A field the composite genuinely cannot render is a finding for
`spec/roadmap.md`, not a `<textarea>`.

--------------------------------------------------------------------------------
PART 3 — CREATE, EDIT, DELETE

- **Create** opens a generated form from the `create` contract's input schema.
- **Edit** opens the same generation from `update`'s input, prefilled from the
  row, and submits only what changed.
- **Delete** requires a confirmation naming what will be deleted. `Confirmation`
  already exists in the vocabulary and `ui.ActionButton` already honours it —
  use it rather than inventing a dialog. Nothing in the platform exposes a
  `delete` today (mesh-serve #69), so this path must degrade to a refusal that
  says so, and a test must cover that case.

Each of the four is optional. A collection with `find` and nothing else renders a
read-only screen with no create button — **not a disabled one and not a hidden
one**: a control that is not part of this collection's surface does not exist,
while a control the caller is merely not allowed to press stays visible, disabled,
and labelled with what is missing. Those are different states and `states.md` §4
is about the second.

--------------------------------------------------------------------------------
PART 4 — THREE THINGS THAT HAVE ALREADY GONE WRONG ONCE

**A scoped collection answers about one organization, and the screen says which.**
`site.find` is `scopedBy: 'tenantId'`, `membership.find` by `organizationId`. The
console shipped a header reading *What this cluster serves* over a scoped read and
it looked right because the only cluster it had run on had one organization. The
composite needs a place for *whose* and must not let a caller quietly omit it.

**A refusal is a state, per contract.** A caller may read and not write: `find` at
`user` and `update` at `operator` is ordinary. `Availability` is already data for
exactly this. All five states reachable; `idle` folds into `loading`.

**A field is not always renderable.** `UserSchema` carries `passwordHash` and
`user.find` cannot be exposed at all because of it — surfdns **V2**. A renderer
that draws every field of every row is where that becomes a leak. Make the safe
direction the default and write the decision down.

--------------------------------------------------------------------------------
WHAT NOT TO DO

- **No `any`, no `as`, no `!`.** Not in the composite, not in its tests. U7 gave
  you `Fields<T>` and generic functions that keep their type parameters; if
  something still will not type, that is a finding worth writing down, not a cast.
  Dispatch 25 used 11 of them in 207 lines.
- **No inline `style: { … }`.** Dispatch 25 wrote four. `ui.css` and the token set
  exist; a composite that styles itself inline cannot be themed and bypasses the
  layer ordering that was fixed this week.
- **Do not hand-roll a list, a table or a form.** `ui.EntityList`, `ui.Table`,
  `ui.DetailSurface`, `ui.PropertyGrid`, `ui.Form`, `ui.ActionCard`,
  `ui.ViewLayout`. This composite is their composition.
- **Do not rename existing props.** Two were renamed on the strength of a roadmap
  note this week and both had to be reverted.
- Do not edit mesh-serve, mesh-web, mesh-operator or flowboard. If the kernel
  lacks something, write it into `spec/roadmap.md` with its evidence and work
  around it here.
- Do not touch `@flybyme/mesh` (frozen).
- Do not build console views. That is mesh-operator's and a different dispatch.

--------------------------------------------------------------------------------
HOW TO EDIT, AND IT IS NOT OPTIONAL

**Edit files with your file tools.** Dispatch 24 in this repository committed
eighteen `.cjs` scripts that read a source file, ran a regex over it and wrote it
back — `fix-table-row.cjs` through `fix-table-row5.cjs`, a record of one pattern
failing to match four times — plus a `sed -i`. A dispatch in mesh-serve did the
same with five `patch_*.js` the next day and **deleted 88 lines of explanatory
comments** doing it. All of them had to be removed by hand, by the person who owns
this platform, who found them himself. Write the change. Do not write a program
that writes the change.

**Commit as you go, in the foreground.** The mesh-serve dispatch reported SUCCESS
having committed nothing, with eight modified files sitting unstaged. When your
turn ends the process exits: a commit survives it and an unstaged edit does not.
Never background `npm test`; wait for it.
